# M3：ConnectX-7 400G の実測結果

2026-10-23 に、KVM 上の 64 vCPU VM 2 台と ConnectX-7 400G DAC 環境で UDP、TCP、CPS を測定した。
測定ソースは **`9e66b63`（v0.22.0 + #152、v0.23.0 と同じコード）** であり、全条件で同じ既存ビルドを使った。
[既存の 100G ベンチマーク](../../benchmark_realnic.md) とは環境が異なるため、結果を分けて記録する。
集計値は [summary.csv](summary.csv) に収録した。

登壇向けの代表値には、TCP は 30 秒持続転送、UDP は約 30 秒の受信処理実績を使う。
各条件は単発測定であり、繰り返し測定による分散は評価していない。

| 対象 | 代表値 | 条件 |
|---|---:|---|
| TCP / Linux 対向 | 318.9 Gbps | 30 秒、32 worker、256 フロー、窓 128、再送 1,442 パケット |
| TCP / XDP 対向 | 239.6 Gbps | 30 秒、48 worker、64 フロー、窓 32、再送 0 |
| UDP / 64 B | 112.4 Mpps | 約 30 秒、32 worker、256 ポート RSS、受信処理の平均 |
| UDP / 512 B | 273 Gbps | 約 30 秒、32 worker、256 ポート RSS、受信処理の平均、FCS を除く |
| CPS / XDP 対向 | 49,996.57 CPS | 30 秒、16 worker、256 スロット、隔離 1 秒、1 接続 1 KiB |

## UDP の生成数、NIC 送信数、受信数

`simpleudp.go` による IPv4/UDP、L2 フレーム長 64 B（FCS を除く）、ペイロード 22 B を使った。
送信元ポートは固定条件で 10000、RSS 条件で 10000〜10255 を走査した。
送信は `--infinite --count 4096`、batch size 64、PPS 制限なし、対向は xdperf の受信モードとした。

| worker 数 / ポート | 送信時間 s | BPF 生成 Mpps | NIC 送信数 | 受信数 | 受信 Mpps | 使用受信キュー数 |
|---|---:|---:|---:|---:|---:|---:|
| 1 / 固定 | 16.088 | 3.194 | 51,380,224 | 51,380,224 | 3.194 | 1 |
| 4 / 固定 | 17.242 | 14.474 | 249,561,088 | 249,287,104 | 14.458 | 1 |
| 16 / 固定 | 17.742 | 41.913 | 743,608,171 | 257,814,466 | 14.531 | 1 |
| 16 / 256 ポート（RSS） | 17.730 | 39.798 | 677,849,763 | 677,849,642 | 38.231 | 30 |

RSS 条件の各段階のカウントは次のとおりだった。

| 段階 | パケット数 | 取得元 |
|---|---:|---|
| BPF 生成 | 705,623,680 | クライアント summary の `tx_packets` |
| NIC 送信 | 677,849,763 | 送信側 `ethtool -S` の `tx_xdp_xmit` 前後差分 |
| 受信 | 677,849,642 | 対向 summary の `rx_packets` |

生成 → NIC 送信の差は 27,773,917（生成数の 3.936%）、NIC 送信 → 受信の差は 121 だった。
xdperf の TX 統計は BPF が `XDP_TX` を返す前に加算するため、NIC の実送信数とは異なる。
後段の送信結果は `diff_errors` や `checksum_errors` に反映されず、両カウンタが 0 でも全量配送を意味しない。

同じ RSS 条件で、送信側の受信 PAUSE（`rx_pause_ctrl_phy`）と対向の送信 PAUSE（`tx_pause_ctrl_phy`）は、それぞれ 794,439 増加した。
`tx_xdp_full` は 1,887,454 増加したが、これは送信キュー満杯の回数であり、失われたパケット数としては扱わない。
対向からのバックプレッシャーも関与し得るため、生成数との差を確定した drop や送信 CPU の限界とは断定しない。
NIC カウンタには背景通信、取得区間、ドライバによる収録範囲の差もあるため、配送状況は受信側と照合する。

固定ポートの 16 worker 条件では受信が 1 キューに集中し、`rx_out_of_buffer` は 485,793,705 増加した。
RSS 条件では 30/63 キューに分散し、同カウンタの増分は 121 だった。

## UDP の追加持続測定

送信元ポート 10000〜10255、`--infinite --count 4096`、PPS 制限なしで、L2 長（FCS を除く）64 B と 512 B を測定した。
下表の NIC 送信数は物理カウンタ `tx_packets_phy` の前後差分であり、先の表の `tx_xdp_xmit` とは取得元が異なる。
受信 Mpps と受信 Gbps は対向の処理数と処理バイト数を送信時間で割った値で、Gbps は FCS を含まない。

| worker 数 / L2 長 B | 送信時間 s | BPF 生成 Mpps | NIC 送信 Mpps | 受信処理 Mpps | 受信処理 Gbps |
|---|---:|---:|---:|---:|---:|
| 32 / 64 | 30.679 | 112.447 | 112.444 | 112.442 | 57.571 |
| 32 / 512 | 30.698 | 66.764 | 66.764 | 66.764 | 273.466 |
| 48 / 64 | 30.526 | 117.365 | 109.147 | 109.146 | 55.883 |

64 B の 48 worker は生成数が増えても受信処理が低下したため、代表値は 32 worker とした。
32 worker / 64 B では `tx_xdp_full` が 5,662、受信側 `rx_out_of_buffer` が 55,949 増加し、生成数と受信数には差がある。
32 worker / 512 B では両カウンタの増分は 0 だったが、PAUSE は両側で 98,817 回、約 2.701 秒増加した。

UDP 1500 B の steering miss は調査中。

## TCP の有限転送

`tcpflow.go` で合計 4 GiB を目標とし、worker 数は `min(フロー数, 16)`、duration 上限は 18 秒とした。
MSS は 1448 B、`window_segs=32`、RTO は 200 ms。
対向は XDP TCP レスポンダまたは Linux の xdperf-sink とした。

| 対向 | フロー数 | 負荷時間 s | ACK 済み量 B | Gbps | done / failed | 再送パケット数 | window_stalls |
|---|---:|---:|---:|---:|---:|---:|---:|
| XDP | 1 | 11.451259 | 4,294,967,296 | 3.001 | 1 / 0 | 0 | 58,448,323 |
| XDP | 16 | 0.553220 | 4,294,967,296 | 62.109 | 16 / 0 | 0 | 30,954,391 |
| XDP | 256 | 0.603646 | 4,294,967,296 | 56.920 | 256 / 0 | 0 | 68,751,761 |
| Linux | 1 | 18.000825 | 2,343,831,264 | 1.042 | 1 / 0 | 0 | 123,007,864 |
| Linux | 16 | 0.803586 | 4,294,967,296 | 42.758 | 16 / 0 | 0 | 116,017,031 |
| Linux | 256 | 0.504484 | 4,294,967,296 | 68.109 | 256 / 0 | 2,802 | 36,205,682 |

多フローの 42.758〜68.109 Gbps は約 0.5〜0.8 秒で終了した有限転送の平均値であり、持続性能ではない。
Linux 1 フローは duration 到達で終了し、目標 4 GiB の 54.57% にとどまった。
正常クローズによる `done=1` は目標バイト数の達成を意味しない。
`window_stalls` は次のセグメントが有効な送信窓に収まらなかった送信判定回数であり、停止時間や損失パケット数ではない。

全 6 条件でフロー CSV の行数と設定フロー数が一致し、全行が done だった。
CSV の `bytes_acked` 合計、クライアント summary の ACK 済み量、受信側のバイト数は一致した。
CSV の `tx_rtx` 合計も summary の再送数と一致した。

## TCP の 30 秒持続転送

`tcpflow.go` の `bytes:"0"`、connections 省略、duration 30 秒、MSS 1448 B、RTO 200 ms とし、接続を作り直さずに送信した。
CPU mode は `auto`、RSS とオフロードは既存設定、XDP レスポンダは `ack_every=1` とした。
平均 Gbps は drain 後の ACK 済み量を負荷時間で割った値であり、定常 Gbps は負荷 2〜29 秒の秒別中央値である。

### XDP 256 フローの低下の切り分け

16 worker / 窓 32 の 64→256 フローで、`window_stalls / data_segments` は 0.73→31.03、`idle_iterations / data_segments` は 0.08→3.56 に増えた。
256 フローでは送信側受信 PAUSE と対向送信 PAUSE がともに 77,406 回、約 4.189 秒増えた。
窓 128 への拡大は平均 62.901 Gbps（約 10% 改善）にとどまり、再送 2,234 と受信側 `rx_xdp_tx_full` 892,305 が発生した。
32 worker / 窓 32 では 190.897 Gbps に改善したが、PAUSE は約 7.420 秒だった。

受信 CPU の継続的な 90% 以上の使用は観測されなかった。
送信側の perf サンプル比率では、64→256 フローで `tcp_tx_decide_mixed` が 0.46→1.72%、spin unlock が 8.43→10.98% となったが、送信待ちのループも含むため原因の確定には使わない。
候補探索は最大 8 件であり、毎回全 256 フローを走査する実装ではない。
送信処理能力と受信側の圧迫は観測されたものの、CPU、PCIe、NIC 内部の寄与は未確定である。
Linux 対向で 318.920 Gbps を観測したため、起動ログの PCIe 252.048 Gb/s を共通の実測上限とは扱わない。

### Linux 1 フローの窓と ACK 観測

先行する追加調査では、1 worker / 30 秒で窓 32 が 0.894 Gbps、窓 128 が 2.293 Gbps となり、両条件とも再送 0 だった。
窓 128 の fexit による観測では RX の ACK のみを取得し、in-flight は spin lock 付きフローマップから約 1 ms 間隔で取得した。
12,000 ACK（3.327 秒）の間隔は中央値 156.4 µs、95% 点 301.4 µs、ACK の進み幅は平均 118,905 B（82.12 MSS）だった。
広告窓は window scale 適用後 1,030,144〜1,139,712 B、in-flight は中央値 112,944 B、最大 185,344 B で、設定窓 128×1448 B に達した。

広告窓が送信窓より大きく再送もないことは、小さい送信窓と集約 ACK の返送待ちによる制約という説明と整合する。
ただし窓 32 の ACK/in-flight 取得は失敗し、窓 128 だけに数秒間の観測負荷が加わったため、窓だけを変えた厳密な比較ではない。
GRO 固有の影響、ACK 遅延の発生箇所、VM スケジューリングの寄与は確定していない。

## CPS とポート隔離の制約

Linux の xdperf-sink 対向、256 スロット、16 worker、1 接続 1024 B、`connections=0`、ポート隔離 10 秒、各 30 秒で測定した。

| 目標 CPS | 実測開始 / 確立 / 完了 CPS | 開始＝確立＝完了＝対向 accepted＝closed | ACK 済み＝受信バイト数 | cps_unmet |
|---:|---:|---:|---:|---|
| 1,000 | 999.981 | 30,000 | 30,720,000 | false |
| 5,000 | 4,999.855 | 150,000 | 153,600,000 | false |
| 20,000 | 5,553.441 | 166,608 | 170,606,592 | true |

全条件で failed、再送、window_stalls、終了時の対向 active は 0 だった。
送信元ポート 10000〜65535 の 55,536 個を 10 秒間隔離するため、上限目安は `55,536 / 10 = 5,553.6 CPS` となり、実測値と整合する。
20,000 CPS 条件では 600,000 回の開始機会に対して、隔離による見送り 416,486、scan 見送り 16,852、late 54、busy 0、service 0 だった。
約 5,553 CPS はこの隔離条件によるポート上限であり、送信エンジンの CPU 上限は測れていない。

### 隔離 1 秒での追加測定

XDP レスポンダ対向、256 スロット、16 worker、1 接続 1 KiB、隔離 1000 ms、各 30 秒で測定した。
CPS は負荷区間内、接続数と ACK 済み量は drain 終了後の値である。

| 目標 CPS | 開始 / 確立 / 完了 CPS | 最終開始＝確立＝完了＝accepted＝closed | ACK 済み＝受信 B | late | cps_unmet |
|---:|---|---:|---:|---:|---|
| 10,000 | 9,999.94 / 9,999.94 / 9,999.87 | 299,999 | 307,198,976 | 1 | true |
| 20,000 | 19,999.03 / 19,999.03 / 19,999.03 | 599,991 | 614,390,784 | 9 | true |
| 50,000 | 49,996.57 / 49,996.57 / 49,996.57 | 1,499,917 | 1,535,915,008 | 83 | true |

全条件で busy、quarantine、scan、service による見送り、再送、RST、failed、終了時 active は 0 だった。
見送りは late のみで、`cps_unmet=true` だが、50k 条件でも目標の 99.99% に達した。
10 秒隔離の約 5,553 CPS は条件による上限であり、1 秒隔離では 50k までの達成を確認した。
送信側の CPS 上限は特定していない。

## 既知の verifier 警告

カーネル 6.17.0-41 では、`xdp_rx_tcp_mixed` の `src/xdp_tcp_decap.h:21`（GENEVE option 解析の `off + 4 > end`）と、encap の `src/xdp_tcp_encap.h:86`（`if (j < l4 - off)`）の範囲推論で `REG INVARIANTS VIOLATION` が出るが、ロードは成功した。
通常の TCP 1 フローで使う 11 プログラムを個別ロードしたところ、encap の警告は `xdp_tx_tcp_mixed` と `xdp_rx_tcp_mixed` で各 36 件、decap の警告は `xdp_rx_tcp_mixed` で 17 件だった。
残る 9 プログラムは警告 0、カーネル 7.0.0-38 では全 11 プログラムが警告 0 でロードに成功した。
個別ロード時は attach と送信を行っておらず、成功時の verifier ログで確認したため、dmesg の新規警告だけでは有無を判定できない。
この比較は実行時の安全性やカーネルの修正箇所を確定するものではない。

## 集計元

元報告書は `M3_REPORT_v022.md` の「v0.22.0 実測」「追加調査」「性能測定 (続き)」節、生データは計測用リポジトリの `out/m3/v022-run/`、`out/m3/v023-extra/`、`out/m3/v023-perf/` に保存した。
本リポジトリには集計 CSV のみを収録し、生ログや大きな health ログは含めない。
集計は保存済みの `summarize.py`、`summary.json` と以下の入力を照合した。

- `udp-*.json` と `udp-*-server.json`：BPF 生成数、送信時間、受信数。
- 各条件の `*-before-host{1,2}.snapshot` と `*-after-host{1,2}.snapshot`：`ethtool -S` の前後差分。PAUSE もここから取得した。
- `tcp-*.json` と `tcp-*.csv`：負荷時間、ACK 済み量、完了状態、再送数。対向 JSON または server ログ末尾の JSON で受信量を照合した。
- `cps-*.json` と server ログ末尾の JSON：接続数、受信量、ポート隔離による見送り。

追加測定は `summary.json`、`udp-summary.json` に加え、元のクライアント JSON、フロー CSV、対向 JSON またはログ末尾の JSON、NIC snapshot を照合した。
窓と worker の比較は `ledger-checks.json`、`diagnostics.json`、`profile-summary.json`、単一フロー観測は `ack-summary.json`、警告は `verifier-summary.json` と `verifier-locations.json` に対応する。
最初の perf 取得失敗 2 条件は主比較から除外し、後続の `perf-diag-*` で置き換えた。
CSV の条件名は各ディレクトリ内の生データの接頭辞に対応し、追加調査の 11 条件と、後続の TCP 26 条件、UDP 3 条件を追記した。

UDP の Mpps は生成数または受信数をクライアントの `elapsed_seconds` と `10^6` で割った値とした。
受信 Mpps は同じ送信時間に換算した区間相当値であり、待機時間を含むサーバー summary の RX PPS とは異なる。
TCP の Gbps は `bytes_acked × 8 / load_seconds / 10^9`、CPS は負荷区間内の開始、確立、完了数を `load_seconds` で割り、drain と linger を時間から除いた。
表の丸め前の時間と整数カウンタは `summary.csv` に残し、該当しない列は空欄とした。
CSV の `実測_CPS` は開始 CPS、`実測確立_CPS` と `実測完了_CPS` はそれぞれ負荷区間内の確立と完了 CPS であり、drain 後の完了接続数から再計算しない。
追加列に測定区分、送信窓、隔離時間、L2 長、UDP 受信 Gbps、定常 TCP Gbps を記録した。
