# TCP フローのパケットひな型とカプセル化

## 対象と段階

`PacketVariantSet` の `kind: "tcp_flow"` に、プラグインが生成する Ethernet フレームを渡せるようにする。
[混合バリアント](design_mixed_variants.md)の配分、終了条件、ポート割り当て、送信記録を維持し、[TCP エンジン](design_xdp_tcp.md)の状態機械を共用する。
この文書の API は段階ごとに実装するものであり、後続段階のフィールドを先行して受理しない。

| 段階 | 実装範囲 | ブランチ |
|---|---|---|
| 1 | グループ別 base_packet、Ethernet、VLAN 最大 2 段、IPv4/IPv6、固定 TCP オプション | feat/tcp-flow-template |
| 2 | 256 バイトのひな型、汎用 TX 修正表、VXLAN/GENEVE RX、VXLAN E2E | feat/tcp-flow-encap |
| 3 | SRv6、GTP-U、GRE、IPIP、MPLS の RX | feat/tcp-flow-rx-tunnels |
| 4 | Timestamps、ペイロードパターン、フロー別 variable_params | feat/tcp-flow-payload |

`--tcp-server` のトンネル対応は対象外とする。
`--tcp` と packet 専用の TX/RX は従来の入口を維持する。
混合集合の packet バリアント必須、pattern=mixed、最大 16 バリアントという条件も維持する。

## フィールドの所有権

エンジンは TCP の seq、ack、flags、window、data offset、送信元ポート、IP/UDP の長さ、チェックサムを更新する。
IPv4 ID は従来の `--tcp-ip-id` に従う。
shared では CPU 別カウンタを使い、per-flow ではひな型の ID を初期値にしてフロー別に増加させる。
TCP の reserved ビットと urgent pointer はひな型から保持するが、URG を含む flags は状態機械が所有する。
ECN 未実装のため、各 IP ヘッダの ECN は 0 にする。
DSCP、TTL、IPv6 traffic class の DSCP 部分と flow label は保持する。
長さとチェックサムの入力値はプレースホルダーとして扱う。
壊れたヘッダ、状態機械に従わない TCP、断片を送りたい場合は packet バリアントを使う。

base_packet を指定した場合はその MAC と IP を使い、経路探索で上書きしない。
送信デバイス、MTU、最大フレーム長は引き続きホストが検査する。
`--tcp-src-ip`、`--tcp-dst-mac`、`--tcp-vlan-*` とひな型の併用は、暗黙の上書きを避けるため拒否する。
base_packet を省略したグループは従来の経路解決とヘッダ生成を使う。

## 段階 1 のプラグイン API

次は混合集合の TCP バリアントだけを抜き出した例である。
`base_packet.data` は SDK の `[]byte` を JSON 化した base64 文字列で、例では Ethernet/IPv4/TCP の最小ヘッダを示す。
長さは実際のバイト数と一致させる。

```json
{
  "kind": "tcp_flow",
  "weight": 1,
  "base_packet": {
    "data": "AgAAAAACAgAAAAABCABFAAAoAABAAD8GAADAAAIBwAACAicQFFEAAAAAAAAAAFAA//8AAAAA",
    "length": 54
  },
  "tcp_flow": {
    "destination": "192.0.2.2:5201",
    "syn_options": "BAIBAQ==",
    "data_options": "AQEBAQ==",
    "flows": [{"bytes": "65536"}, {"bytes": "262144"}]
  }
}
```

destination は base_packet があれば省略できる。
両方指定した場合、内側 TCP の宛先 IP と宛先ポートの一致を検証する。
グループ間で宛先が異なってもよい。
フロー番号と送信元ポートの割り当ては全グループを通じて一意にする。
base_packet は TCP 固定ヘッダまでとし、TCP オプションは専用フィールドに渡す。
TCP data offset の入力は使用せず、生成するオプション長から決める。
IPv4 options、IPv6 拡張ヘッダ、断片、TCP 後方のペイロードを段階 1 では拒否する。
`variable_params` と `checksums` は引き続き拒否する。

`syn_options` と `data_options` も base64 のバイト列である。
ホストは SYN の先頭に従来の MSS(4) + NOP(1) + WS(3、値 7) を追加する。
ユーザー指定の SYN オプションは最大 32 バイト、データ用は最大 40 バイトで、4 バイト境界になるよう末尾を NOP で埋める（EOL 後はゼロで埋める）。
NOP、EOL、SACK-Permitted、実験用オプションなど、セグメントごとに内容が変わらない TLV を保持する。
EOL 以降はゼロのパディングだけを許可する。
不正な TLV 長、重複するエンジン所有の MSS/WS、Timestamps、SACK ブロック、MPTCP、TFO、TCP-AO、TCP-MD5 は拒否する。
Timestamps は段階 4 の専用指定でのみ有効にする。
受信 SACK ブロックは無視し、既存の go-back-N 再送を続ける。

MSS はデバイス MTU とフレーム上限から、L2 の追加タグ、IP、TCP、データ用オプションを引いた上限に収める。
従来の既定 MSS を出発点とし、追加ヘッダ分を減らす。
明示 `--tcp-mss` はオプションを除く基準値として扱い、追加オプション分を差し引く。
SYN の全長も独立に検証する。
相手の広告 MSS からもデータ用オプション分を差し引き、フローの有効 MSS を更新する。
最小有効 MSS は既存の 64 バイトとする。

## BPF マップと送信

既存の `tcp_cfg_map` は全体の flow_count、port_base、drain/abort と従来モードの設定を保持する。
`tcp_template_map` (ARRAY、最大 16) にグループ別の不変設定を格納する。
`tcp_flow` に template_id を追加し、フロー選択後の 1 lookup でグループを得る。
状態機械にはグループ別 MSS と従来の制御設定を渡す。
終了制御を書き換える際はグループ側にも drain/abort を伝える。

段階 1 の値は次を含む。

- `tcp_cfg`：アドレス、ポート、pseudo_sum、MSS、L3/L4 オフセットと既存の再送設定。
- `prefix`：TCP の手前までのバイト列。段階 1 は最大 64 バイト、段階 2 は 256 バイト。
- `tcp_header[20]`：プラグイン所有の固定ビットを保持するための固定ヘッダ。
- `syn_options[40]`、`data_options[40]` と各長さ。

混合 TX は専用 builder で prefix を復元し、TCP ヘッダとオプションを生成する。
混合 packet が残したデータや、以前の SYN オプションを送らないように、一度 TCP 固定ヘッダまで縮小してからゼロで拡張する。
TCP チェックサムはアドレスの事前計算値と生成ヘッダの和から求める。
段階 1/2 のペイロードはゼロであり、ペイロード全体を走査しない。
RX が返す ACK/RST も同じ builder を使う。
これにより QinQ の復元、グループ固有の DSCP/TTL、トンネルへの再カプセル化を TX と共通化する。
RX におけるフロー別 IPv4 ID の採番はフローロック内で行う。

## 段階 2 の修正表

BPF はトンネルの種類に依存せず、prefix と検証済みの修正表を実行する。
Go は既知の構造を解析し、プラグインが指定したオフセット、種類、固定値と照合する。
修正表をホストが暗黙に補完することはしない。
内側 IP の長さとチェックサムはエンジンが常に処理し、表は外側ヘッダを対象とする。
次は Ethernet/IPv4/UDP/VXLAN/Ethernet/IPv4/TCP の例である。
オフセットはフレーム先頭から、segment_len は内側 TCP ヘッダ、オプション、ペイロードの合計と定義する。

```json
{
  "encapsulation": {
    "inner_l3_offset": 64,
    "inner_l4_offset": 84,
    "lengths": [
      {"offset": 16, "kind": "ipv4", "constant": 70},
      {"offset": 38, "kind": "udp", "constant": 50}
    ],
    "ipv4_checksums": [14],
    "udp_checksums": [{"offset": 34, "ip_offset": 14, "mode": "zero"}],
    "udp_source_port": {"offset": 34, "base": 49152, "count": 16384}
  }
}
```

`encapsulation` は `tcp_flow` の子要素とする。
各修正表は外側から内側への解析順に並べ、欠落と重複を拒否する。
lengths の kind は ipv4 (total length)、ipv6 (payload length)、udp、gtpu を区別し、各値はネットワークバイト順の uint16 とする。
実行時は constant + segment_len のオーバーフローを検査する。
udp_source_port は base + flow_index % count を使い、再送や RX 応答でも同じ値にする。
base、count と合計がポート範囲に収まり、指定位置が解析済み外側 UDP の source であることを検証する。

外側 UDP チェックサムは IPv4 のみ zero を許し、IPv6 では lco を必須とする。
LCO は、正しい内側 TCP チェックサムが書かれていることを前提に、内側 TCP 全体の和を TCP 擬似ヘッダ和の補数から求める。
UDP 擬似ヘッダ、UDP ヘッダ、UDP 直後から内側 TCP 手前までのヘッダを加え、ゼロ結果は 0xffff にする。
奇数オフセットではバイトの位相を入れ替える。
UDP が多段の場合は内側から計算し、外側が既に確定した内側チェックサムを参照する。
ペイロード長に比例する走査を避ける。

ひな型上限 256 バイトは TCP 固定ヘッダまでを含む。
最大修正数は長さ 8、IPv4 チェックサム 4、外側 UDP チェックサム 4、解析の入れ子 4 層とする。
Go は VXLAN、GENEVE、GTP-U、SRv6、GRE、IPIP、MPLS の長さと構造を照合する。
未知の構造、IPv4 options、断片、未対応の拡張機能は理由付きで拒否する。
GENEVE の可変オプション長、GTP-U の optional fields、GRE の optional key、MPLS の bottom-of-stack を解析し、境界を確認する。
対応する送信構造と受信構造が異なる期間は、未対応の RX を利用する設定を明確に説明する。

## 受信側とフロー照合

混合 RX には専用の TCP 解析器を置き、既存 `--tcp` と packet 専用 RX の実行命令を増やさない。
Ethernet と最大 2 段の VLAN を解析し、既知のカプセル化を上限付きで順に外す。
各層の申告長を親層の終端とフレーム終端の両方に照合する。
IP の version、IPv4 IHL、IPv6 next header、断片化、UDP 長、VXLAN I flag、GENEVE version/critical flag/option 長を検査する。
上限超過、未対応の構造、断片はフロー状態を更新せずホストへ渡す。
対象フローと判定した後の不正 TCP 長は DROP する。

内側 TCP の宛先ポートからフロー番号を取り、template_id のアドレスと相手ポートで内側 5 タプル全体を照合する。
外側 IP、VNI、MAC、UDP ポートはフローのキーに含めない。
同じ内側タプルならカプセル化なしの応答も受理する。
送信元ポートは全フローで一意なので、異なるトンネル内のフローも区別できる。
これにより外側の送信経路が非対称でも動作するが、外側属性をセキュリティ境界として検証する用途は対象外である。

段階 2 では VXLAN と GENEVE を外せるようにする。
トンネル内の ARP と IPv6 ND（ICMPv6 type 133〜137）はホストの近隣解決へ PASS し、外側 UDP の計測には含めない。
それ以外の未一致 UDP は従来の --recv の外側 UDP 計測へ渡し、対象 TCP の RX 応答はグループの送信テンプレートを使って返す。
段階 3 で SRv6 (SRH の長さと segments_left)、GTP-U (G-PDU、拡張ヘッダの上限)、GRE (version/flags)、IPIP、MPLS (ラベル最大数と IPv4/IPv6 判定) を追加する。
これらの解析でも外側のアドレスを照合条件に加えない。

## verifier と古いカーネル

可変オフセットを足したスタックポインタによるアクセスを作らない。
TCP/IP の編集は固定サイズのローカル配列か境界検査済みのパケットポインタで行い、マップ内の prefix は固定オフセットの小ブロックとしてコピーする。
256 バイトの prefix をスタックに全コピーせず、展開したコピー処理でマップからフレームへ書く。
末尾の部分ブロックには定数サイズの書き込みを使う。
すべての可変オフセットに上限を置き、加算前の範囲検査と data_end の検査を併用する。
helper を呼ぶときは bpf_spin_lock を保持しない。

#121 では小さなループも古い verifier の状態数増加を招いたため、コピー、固定長チェックサム、短い VLAN 走査は明示的に展開する。
トンネルの解析は深さに固定上限を置く。
`bpf_loop` の追加依存は作らず、既存 helper の最低要件を維持する。
コンパイル成功だけでは合格にせず、ローカル BPF ロード、BPF_PROG_RUN、CI と既存の vimto カーネル行列を確認する。
拒否された場合は verifier ログから可変スタックアクセスと状態数を調べる。

## 段階 4 の設計

### 段階 4 の実装計画（ジョブ C）

段階 4 は `feat/tcp-flow-payload` で実装し、PR の base を `feat/tcp-flow-rx-tunnels` とする。
以下の三機能を同じテンプレート生成経路に追加する。
未使用時は起動時に設定する BPF 定数で分岐と補助関数を検証対象から除き、通常 TCP と packet 専用の入口に処理を追加しない。

- **Timestamps**：`tcp_flow.timestamps` だけをプラグインの指定とする。SYN と通常セグメントのオプション先頭に 12 バイト（NOP、NOP、kind=8、length=10、TSval、TSecr）をエンジンが生成する。SYN-ACK で合意しなければ以後は付けない。TSval は単調時計のミリ秒を 32 bit に切り詰め、フローロック内で非減少にする。TSecr と PAWS 用の TS.Recent をフロー状態に保持する。[RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html) に従い、古い timestamp と合意後の timestamp 欠落は状態更新から除き、RST は timestamp の有無で排除しない。24 日を超える TS.Recent は失効させる。オプションの合計は 40 バイト以下に制限し、EOL より前にエンジンのオプションを置く。
- **ペイロードパターン**：`tcp_flow.payload_pattern` を最大 256 バイトの base64 列とする。未指定と全ゼロは既存のゼロ生成へ正規化する。送信決定と同じフローロック内で `bytes_acked + uint32(seq - snd_una)` を求め、64 bit のストリーム位置から繰り返しパターンを選ぶ。再送、短い末尾、4 GiB 超、seq ラップで同じ内容を生成する。パターンの繰り返しを最大 512 バイトの偶数周期へ拡張し、16 bit 語の部分和を起動時に用意する。チェックサムは周期和と端数の差分で求め、送信時の書き込みだけをペイロード長に比例させる。外側 UDP の LCO は既存の内側 TCP チェックサムを使う。
- **フロー別 variable_params**：明示的な base_packet を必須とし、起動時に sequential または mixed を一度だけ評価する。まず安全な許可範囲として内側送信元 IP のバイト部分範囲を扱う。宛先、ヘッダ構造、長さ、ポート、オプション、チェックサムなどのエンジン所有領域は拒否する。各フローの確定済みテンプレートと擬似ヘッダ和を既存テンプレートマップに展開し、RX も同じ値で照合する。追加 lookup は不要とする。マップは必要なエントリ数にだけ拡張し、値領域を 64 MiB 以下に制限する。drain/abort と再送も展開済みテンプレートを使う。

variable_params の任意オフセットを一括で許可すると、カプセル化識別子と受信照合、外側 UDP 擬似ヘッダ和の所有権が曖昧になる。
このため段階 4 の初期 API は内側送信元 IP に限定し、未対応範囲は明示的なエラーにする。
全フロー分のペイロード部分和を複製するとメモリが増えるため、パターンは最大 16 個のグループ別マップに分離する。

検証は Go の入力検査、BPF_PROG_RUN による生成バイト列と独立チェックサム照合、Linux TCP 対向の veth E2E を組み合わせる。
Timestamps の合意と非合意、SYN 再送、PAWS、timestamp のラップ、再送時の同一ペイロード、フロー別 IP による RX の正負照合を含める。
全 sudo race テスト、全 examples、lint、OCR を完了して PR を作成し、Copilot と CI を確認する。

性能は既存 mixbench と同じ veth、CPU 配置、MSS、window、batch を用い、未使用の既存混合 TCP と packet 専用を比較する。
6 ブロックで条件順と base/head 順を無作為化し、各対は隣接実行する。
スループットと起動時間について対応差の平均と両側 95% CI（t 分布）を報告し、CI が広い場合は同等と断定しない。
生データとビルド物は `out/job-c/`、`out/mixbench/` と既存 scratchpad の `mixbench/tcp-flow-payload/` に保存し、Git には結果表、小さな summary CSV、検算スクリプトだけを残す。

`tcp_flow.timestamps: true` はエンジン生成の TSval/TSecr を有効にする。
SYN でネゴシエーションし、未対応の相手には送らない。
TSval は単調クロックから作り、TSecr は受信した timestamp をフロー状態に保持する。
再送時刻、PAWS、32 bit ラップ、SYN 再送中の値をテストし、オプション長を MSS とチェックサムに反映する。

`tcp_flow.payload_pattern` は最大 256 バイトの base64 列を指定する予定である。
ストリーム開始からの 64 bit オフセットで pattern[index % length] を選ぶ。
再送位置は bytes_acked と seq の差から復元し、4 GiB 超と seq ラップでも同じ中身を生成する。
ゼロパターンには従来の定数時間チェックサムを使い、一般パターンは周期の部分和を事前計算する。

`variable_params` は起動時にフロー単位で評価し、セグメントごとには変化させない。
エンジン所有範囲との重なり、ヘッダ種別や長さの変更を拒否する。
アドレス変更時は擬似ヘッダ和と受信照合情報をフロー単位に保持し、全フローを展開するメモリ上限を別途定める。
MPTCP、TFO、TCP-AO/MD5 はこの段階でも実装せず拒否する。

## 検証と性能

単体テストでは不正な base 長、EtherType、VLAN 深さ、IP version/fragment、宛先不一致、TLV、禁止オプション、MSS 境界、修正表の不足/重複/重なり/範囲外を検証する。
BPF_PROG_RUN では SYN、データ、短い末尾、FIN、再送、RX の ACK を取り出し、Go 側でチェックサムとバイト列を独立に検証する。
2 グループ以上の MAC/IP/DSCP/TTL/オプションが混ざらないこと、QinQ、IPv6 flow label、RX の長さ検証、カプセル化なし応答、UDP LCO とエントロピーを含める。
混合フレームの再利用には非ゼロの入力データを使い、ペイロード汚染を検出する。

veth E2E は sudo で、送信側 xdperf と受信 netns の xdperf-sink を使う。
段階 1 は Ethernet、VLAN、QinQ、IPv4/IPv6 と複数グループを検証する。
段階 2 は Linux vxlan デバイスの内側でカーネル TCP を終端し、accepted/closed、受信バイト、送信 ledger の bytes_acked を照合する。
既存 examples と全 Go テストも実行し、BPF オブジェクト再生成後に検証する。

性能の合格条件は既存の `--tcp` と packet 専用の送受信ホットパスに追加 lookup、コピー、解析を入れないことである。
追加マップのロード時メモリとフロー構造体の増分は別途報告する。
混合 TCP ではグループ lookup、prefix コピー、オプション処理、RX パースの分だけ費用が増える。
命令数と BPF_PROG_RUN の duration を同条件で比較し、実 NIC の PPS/Gbps は測定環境がある場合に記録する。
veth の成功から実 NIC のスループットを推定しない。

## 未解決の論点と実装時の判断

- 未知の固定オプションは TLV と禁止 kind の検査で受理する。未知オプションの意味をホストが保証することはできない。
- 256 バイトと各修正表の上限で表現できない入れ子は拒否する。上限の拡張は verifier と性能の測定後に判断する。
- RX のハードウェア VLAN stripping は復元された送信ひな型で吸収する。外側属性を照合しないため、VLAN の認証機能にはならない。
- LCO は内側チェックサムが有効であることが前提である。段階 4 のペイロード生成を追加する際も、この不変条件を維持する。
- IPv6 拡張ヘッダと SRv6 の TCP 擬似ヘッダ宛先は区別する。SRH 配下の内側 TCP と、SRH が TCP 自身の IPv6 ヘッダに付く形を混同せず、後者は明示的な対応まで拒否する。
- 手元に古いカーネル VM がない場合、CI の検証結果と未実施範囲を PR に明記する。

## 段階 1 の測定記録

clang-22 で生成した BPF 命令数は、packet TX 391、packet RX 176、通常 TCP RX 1126 で変更前と同じだった。
通常 TCP TX は再送統計のコンパイラ生成差により 1086 から 1088 命令になったが、追加 lookup やひな型処理は含まない。
混合 TCP TX は 1117 から 2058 命令、新設の混合 TCP RX は 2221 命令である（命令数はスループットの測定値ではない）。
フローの template_id は既存のアラインメント用空間に置き、tcp_flow_map の値サイズ 120 バイトを維持した。
グループマップの値領域は全 16 エントリで 5120 バイト増える。

## 段階 2 の実装上の判断

段階 2 は汎用 TX、VXLAN/GENEVE RX、Linux VXLAN 相手の IPv4/IPv6 E2E を実装する。
GRE checksum、routing、sequence (S) フラグは拒否する。
合意した修正表には GRE checksum の種類がなく、長さ変更後の正しい値を生成できないためである。
sequence をひな型の固定値のまま繰り返すと、重複・逆順を検出する対向が後続パケットを破棄し得る。
同じ理由で GTP-U の S ビットと、N-PDU 番号を有効にする PN ビットも拒否する。
トンネル単位の採番を実装するまでは S ビットを受理せず、プラグイン所有バイトを無条件に保持する原則の例外とする。
key のバイトは保持し、version 0 の GRE、IPIP、SRv6、GTP-U、MPLS の送信ひな型を解析して照合する。
これらをカプセル化した応答の受信は段階 3 とし、カプセル化なしの応答は段階 2 でも受理する。
SRH は内側 IP または Ethernet を包む形に限定し、TCP/UDP が SRH の直後にある形は擬似ヘッダの宛先が変わるため拒否する。

外側 IPv4 ID は shared モードでは内側と同じ CPU 別採番値に更新し、それ以外ではひな型の値を保持する。
内側 IPv4 ID のフロー別採番は従来どおりである。
固定オプションのチェックサム和は Go で事前計算し、BPF がオプション列を加算する際のレジスタ退避を減らした。
ひな型を 8 バイトずつコピーし、端数が TCP 固定ヘッダへ重なる部分は後からエンジンの TCP ヘッダで上書きする。
これにより 256 バイト全体をスタックに置かずに復元できる。

受信の層走査は最大 5 回（外側 4 層と内側 TCP）を展開する。
GENEVE のオプション検査は別関数で最大 41 回を展開する（外側 IPv4・raw IPv4 GENEVE では最小オプションが 41 個で 254 バイト、内側 Ethernet 付きでは 38 個で 256 バイト）。
可変オフセットのパケットポインタをコンパイラが組み替えて境界証明が失われる箇所は、固定サイズの `bpf_xdp_load_bytes` で読む。
外側 IPv4 の編集も固定サイズのローカル配列を使う。
LCO はチェックサム確定済みの内側 UDP から外側へ計算し、TCP ペイロードを走査しない。

## 段階 2 の測定記録

段階 1 と比較すると、packet TX/RX と通常 TCP TX/RX は生成バイトコードが同一だった。
命令数はそれぞれ 391、176、1088、1126 である。
混合 TCP TX は 2058 から 14421 命令、混合 TCP RX は 2221 から 17497 命令になった。
増加分には旧カーネルの verifier 向けに展開した境界検査と LCO 処理が含まれる。

全プログラムを通常モードでも検証すると、手元の E2E では受信側の起動が 5 秒の待機上限を超えた。

### 環境と測定方法

測定機は AMD EPYC 7713P として公開された KVM ゲスト（32 vCPU、1 NUMA ノード）、Linux `7.0.0-38-generic` である。
CPU 周波数は `/proc/cpuinfo` 上では全試行で約 2 GHz だったが、cpufreq の governor は公開されておらず、ホストの物理 CPU 周波数や割り当ては制御していない。
送信 worker は 1 個なら CPU 4、4 個なら CPU 4–7 に固定し、送信プロセスの他スレッドは CPU 4–11、sink は CPU 12–15 に制限した。
測定中にローカルでビルドやテストを並行実行せず、各試行の前後に CPU 情報、`/proc/stat`、load average、プロセス一覧を保存した。

各試行で専用の netns 2 個と、両端それぞれ 4 RX/TX queue の veth を作り直した。
送信側は native XDP、対向は Linux TCP と `xdperf-sink -xdp-pass-dev mbrx` であり、veth の XDP_TX に必要な対向 XDP_PASS を attach した。
アドレスと MAC は固定し、近隣エントリを permanent に設定した。
UDP/5353 は受信 netns の INPUT で破棄し、ICMP 応答とユーザー空間 UDP 受信処理の負荷を避けた。
したがって packet の指標は生成側 TX pps であり、UDP のアプリケーション受信性能を示さない。

`--pps` は指定せず、batch size は 64、packet pool は 128、TCP は 4 フロー、MSS 1024、送信ウィンドウ 32 セグメントとした。
混合の `--duration` は既存 CLI の検証で `--pps` を要求するため、各フローの目標を 1 TiB とし、開始から 8 秒後に SIGINT で drain を開始した。
packet のみは `--infinite` を使った。
packet のみの UDP フレームは 74 バイト、混合の DNS フレームは 71 バイトである。
混合の重みは packet:TCP の順で、base_packet、VXLAN、GENEVE はいずれも 3:1 とした。
base_packet は Ethernet/IPv4/TCP、トンネルは外側 IPv4/UDP に内側 Ethernet/IPv4/TCP を入れ、VNI 7、トンネルオプションなし、外側 UDP チェックサムは LCO とした。
TCP の追加 SYN/data オプションは指定せず、対向の Linux VXLAN/GENEVE デバイスで終端した。

18 条件を 6 ブロック、計 108 試行測定した。
ブロック内の条件順と、同じ条件に対する隣接した #121/#123 の順を seed 121123 でランダム化した。
予備実行は集計から除き、本測定の外れ値除去は行っていない。
本測定では `kernel.bpf_stats_enabled=0` とし、BPF 実行時間の補助計測は別に行った。

アプリケーションのログ時刻は秒単位なので、測定スクリプトが各行の到着時刻を monotonic clock で記録した。
混合の pps と goodput は最終カウンタを開始から drain 開始までの実時間で割った。
データセグメント/s は `(tx_data + tx_rtx) / 秒`、goodput は `bytes_acked × 8 / 秒`（10 進 Mbit/s）である。
最終 ACK 済みバイト数には drain 開始時に送信中だった最大 4 ウィンドウ（128 KiB）が含まれ、FIN と linger の時間は分母に含めていない。
packet のみは 2^20 回の送信バッチの終了時刻が worker 間でずれるため、主表では毎秒カウンタの第 1〜7 サンプル間（約 6 秒）の差を実経過時間で割った定常区間の pps を使う。
この集計規則は 1 ブロック目の停止処理の影響を確認した後、2 ブロック目の途中で全 packet 試行に共通と定めた。
最終カウンタを全 worker 終了までの時間で割る値も併記し、生データを保持した。

表の対応差は同じブロックの `#123 − #121` の平均、百分率は各対の `100 × (#123 / #121 − 1)` の平均である。
95% 信頼区間は対応差の標本標準偏差 `s` に対して `平均 ± 2.57058 × s / √6`（両側 t 分布、自由度 5）で求めた。
#123 のみの条件はその平均の信頼区間を示し、#121 との差は定義しない。
各区間は条件ごとの区間であり、多重比較の補正は行っていない。

### BPF ロードと実行時間の補助計測

起動時間の主表はプロセス起動から送信開始までで、WASM、マップの準備、verifier、JIT を含む。
「BPF 初期ロード」は `calculated diff_map size` から `xdperf xdp code loader initialized` までの観測区間である。
「プラグイン応答後」は応答ログから送信開始までで、#123 の混合専用プログラムの追加ロードを含む。
いずれも純粋な verifier の CPU 時間ではない。

本測定とは別に、各組み合わせを 1 回ずつ `strace -f -T -e trace=bpf` で起動し、`BPF_PROG_LOAD` の経過時間を合計した。
packet のみは #121 が 2.292 秒、#123 が 2.284 秒、混合 3:1 はそれぞれ 2.304 秒、6.240 秒だった。
#123 の混合 TCP RX のロードは 2.070 秒、混合 TCP TX は 1.846 秒であり、主測定で観測した約 3.9 秒の起動時間増加と整合する。
この内訳は syscall の時間（検証と JIT を含む）であり、6 反復の起動時間表とは別の診断値である。

## 段階 3 の実装前計画

比較元は `perf/mixed-startup` の `ad72a7f` とする。
受信フレームの各層の申告長を検査し、SRv6、GTP-U、GRE、IPIP、MPLS を順に外して内側 TCP の 5 タプルを照合する。
外側アドレス、GRE key、MPLS label、GTP-U TEID、SRH の segment list は照合に使わない。
送信時と異なるカプセル化、異なる SRH 長、途中でカプセル化が外れた IPv4/IPv6 の応答も受理する。
解析上限は既存の TCP オフセット 236 バイト、外側 IP 4 層を維持し、MPLS は最大 8 label、GTP-U の拡張ヘッダは最大 8 個とする。
未対応の形式、境界違反、断片、上限超過ではフロー状態を変更しない。

SRH は Routing Type 4、Hdr Ext Len、Last Entry、Segments Left の整合性を検査し、内側 IP または Ethernet を解析する。
TCP 自身の IPv6 ヘッダに SRH が付く形式は従来どおり対象外とする。
GRE は version 0 の key あり／なしを受理し、checksum、routing、sequence は対象外とする。
MPLS は bottom-of-stack まで進み、その直後の IP version から IPv4/IPv6 を選ぶ。
GTP-U は GTPv1-U の G-PDU と申告長を検査し、E/S/PN に伴う共通 optional fields と拡張ヘッダ列を読み飛ばす。
受信の S/PN は内側 TCP の照合に使わず、送信とは別に受理する。
構造の根拠は [RFC 8754](https://www.rfc-editor.org/rfc/rfc8754.html)、[RFC 2890](https://www.rfc-editor.org/info/rfc2890/)、[3GPP TS 29.281](https://www.etsi.org/deliver/etsi_TS/129200_129299/129281/16.02.00_60/ts_129281v160200p.pdf) とする。

送信 GRE sequence と GTP-U S/PN の採番はこの変更に含めない。
同じトンネルを共有する複数フローと CPU の TX、再送、RX 応答を通した採番が必要であり、現在のフロー別カウンタではトンネル全体の順序を表現できない。
共有状態と同期を TX ホットパスへ追加する変更は受信解析の拡張から分離し、従来の設定拒否を維持する。

ジョブ A の TX と RX 応答 builder の機能選択を維持する。
送信テンプレートから受信トンネルを限定する案は、非対称経路の受理要件を破るため採用しない。
代わりにプロトコル固有の処理を BPF サブプログラムへ分離し、該当する受信ヘッダを検出した場合にだけ呼ぶ。
通常 packet と `--tcp` は混合 RX 自体をロードせず、従来の命令とロード順を保つ。
混合 RX の verifier 負荷は実測し、展開による状態数増加があれば解析層の関数境界を見直す。

検証では BPF_PROG_RUN で各形式の SYN/ACK、データ ACK、FIN を入力し、状態遷移、再カプセル化した応答、チェックサムを検査する。
異なる SRH 長、GRE key の有無、MPLS の複数 label と IPv6、GTP-U の拡張ヘッダと S/PN、異種トンネルの入れ子、不正長と切り詰めも対象にする。
Linux 対向の ip6tnl/seg6、gre/gretap/ip6gre、MPLS router/lwtunnel、利用可能なら gtp モジュールを使い、完了フロー数と sink の受信バイト数を照合する。
利用できない機能は実行結果を記録し、BPF_PROG_RUN による代替範囲を PR に明記する。
全 sudo race テスト、examples E2E、lint、OCR を完了してから PR を作成し、Copilot と CI を最後まで確認する。

性能は既存 mixbench と同じ対応比較の方式を使う。
起動時間と既存の非カプセル化／VXLAN／GENEVE の性能を 6 対以上で測定し、対応差の平均と t 分布による両側 95% CI を記録する。
生データと再集計手順を残し、差が不明確な場合は同等性を断定しない。

### 段階 3 の実装時の判断

各 IP 層へ全分岐を展開する最初の実装は、verifier の 100 万検証命令上限を超えた。
1 層の解析を独立検証される global BPF サブプログラム `tcp_parse_layer` に分離し、呼び出し側は最大 5 層を進む構成へ変更した。
追加のマップや tail call は使わず、通常 packet と通常 TCP のロード対象も維持する。
混合 RX の入口も新しい EtherType と IP protocol を解析器へ振り分ける。

GTP-U の受信では spare bit と E=0 の未使用 Next Extension Header 値を無視する。
送信ひな型の厳格な検査とは区別し、TS 29.281 の受信規則に合わせる。
S/PN ありの受信、8 個の拡張ヘッダ、8 label、4 外側 IP 層、TCP オフセット 236 バイトの正例と、それぞれの上限超過を BPF_PROG_RUN で確認する。
各正常フレームを全バイト境界で切り詰め、フロー構造体全体が不変であることも検査する。

Linux 対向の SRv6 では、IPv4 を End.DX4、IPv6 を End.DT6 と local table 255 で終端する。
main table を指定した初期設定では、IPv6 の内側宛先がローカル配送されず TCP が完了しなかったため、終端アドレスの local route を引く構成に修正した。
返信は seg6 lwtunnel で 1 segment と 2 segments を生成し、bare IP の返信も別ケースで確認する。
IPv6 GRE/IPIP は `encaplimit none` を指定し、今回の対象外である汎用 Destination Options を付けない。
GTP-U の IPv6 PDP はカーネルが要求する /64 prefix を登録し、実際の TCP アドレスとの照合は通常の内側 5 タプルで行う。

既存の全パケットを層ごとの global 関数へ渡した版では、正式測定前の短い予備実行で既存ケースの送信レートが低く出た。
他テストと並行した 1 対だけの値なので性能差の推定には使わないが、既存経路へ追加した関数呼び出しを除く構成を検討した。
最終構成は bare/VXLAN/GENEVE の従来の走査を一つの global サブプログラムとして保ち、新しい形式を検出した場合だけ汎用の層別走査へ進む。
既知の送信テンプレートから RX を削除せず、受信ヘッダによる分岐で既存経路の呼び出し数を維持する。
二つの走査器が共通に受理する形式は既存の最大 GENEVE 長と混在入れ子のテストで検証する。
全機能を層別走査だけで扱った版の予備データは `out/mixbench/pilot/`、最終構成の予備データは `out/mixbench/pilot-fast/` に残し、正式測定には混ぜない。

Linux 6.1/6.6 の CI では、従来の走査器から拡張走査器を直接呼ぶ構成が合計 544 バイトのスタックを使い、512 バイト上限で拒否された。
新形式を検出したら従来の走査器から呼び出し元へ戻し、そのフレームを解放してから拡張走査器を呼ぶ構成に変更した。
新しいカーネルだけでなく、既存 CI の全カーネルでロードと BPF_PROG_RUN を検証する。

## 段階 4 の実装仕様

### 専用入口とフロー別テンプレート

`timestamps` または非ゼロの `payload_pattern` を含む集合だけが、拡張用の混合 TCP TX/RX 入口をロードする。
指定しない集合と全ゼロのパターンは従来の入口を使う。
通常 TCP と packet 専用の入口から、拡張 builder とペイロード生成器を呼ばない。
variable_params だけを使う場合も従来の混合入口で処理できる。

グループ用のテンプレート番号 0〜15 を残し、variable_params を持つグループのフローには 16 以降を割り当てる。
展開された値は既存マップに置くため、TX と RX の lookup 数は増えない。
必要なエントリ数のマップはプラグイン検査後、worker と RX の起動前に作り直す。
値領域の上限は 64 MiB で、パターンは 16 エントリの別マップに置き、テンプレートの payload_id から共有する。
終了時の drain/abort も展開された全テンプレートへ伝える。

### プラグインの指定と制限

次は TCP バリアントの追加フィールドの例であり、base_packet の内側 IPv4 ヘッダが Ethernet 直後にある場合を示す。
variable_params は tcp_flow の内側ではなくバリアント直下に置く。

```json
{
  "variable_params": [
    {
      "byte_start": 26,
      "byte_size": 4,
      "byte_range": {"start": 3221225995, "end": 3221225998},
      "pattern_type": "sequential"
    }
  ],
  "tcp_flow": {
    "timestamps": true,
    "payload_pattern": "ASP+",
    "flows": [{"bytes": "4097"}, {"bytes": "65539"}]
  }
}
```

内側送信元 IP の部分範囲を、既存 SDK と同じネットワークバイト順で指定する。
byte_size は 1、2、4、6、8 に対応し、範囲外の値、重なり、未定義の pattern_type を拒否する。
sequential はフロー順に進めて範囲末尾で戻り、mixed は起動時にフローごとに抽選する。
実際に生成されたアドレスが unspecified または multicast になった場合も起動を拒否する。
変更できる範囲が送信元アドレスだけなので、base_packet から指定した destination は変化しない。

Timestamps の 12 バイトは SYN/通常オプションの先頭に追加する。
MSS/WS の 8 バイトと合わせ、ユーザーの SYN オプションは最大 20 バイト、通常オプションは最大 28 バイトとなる。
相手が Timestamps を拒否した場合、以後のオプションには追加しないが、ローカル MSS で予約した 12 バイトは戻さない。
RTT による RTO の動的推定は追加せず、既存の再送タイマーを使う。

ペイロードは stream_offset に対応する繰り返し列であり、TCP シーケンス番号の下位 32 bit をパターン位置に流用しない。
奇数長のパターンは 2 周分へ拡張して偶数周期とし、部分和を使うときに開始位置のバイト位相を補正する。
TCP builder が戻った後、外側 IP/UDP の修正、16 バイト単位の bpf_loop によるペイロード書き込みを順に実行する。
これにより builder、カプセル化修正、書き込み、callback の各フレームを必要以上に同時に積まず、512 バイト制限を守る。
`bpf_loop` は既存の packet チェックサム経路でも使用している helper であり、新しいカーネル最低要件を加えない。

[追加 E2E](../../examples/tcp-payload/README.md) は、Linux TCP 相手に IPv4/IPv6 のそれぞれで合意、非合意、パターン、フロー別 IP、併用、ACK 損失下の併用を実行する。

## 混合 RX の照合失敗を数える (ジョブ E、実装前計画)

通常応答の解析と照合に診断用の分岐や書き込みを追加しない。
`xdp_rx_tcp_mixed` の既存の unmatched 経路からのみ cold な別関数を呼び、パケットを再解析して分類する。
照合後の不正 TCP ヘッダによる DROP も、その失敗分岐だけで数える。
既存の packet、単独 `--tcp`、TCP server、混合 TX の命令列は維持する。

分類は独立した 1 要素の PERCPU_ARRAY (`mixed_rx_stats_map`) の配列とし、1 フレームにつき次のいずれかを 1 回加算する。

| ログ名 / OTLP の reason | 意味 |
| --- | --- |
| `rx_parse_failed` / `parse_failed` | TCP に到達できない。未対応形式、解析深度やオフセット上限、長さ不整合、IPv4 オプションや断片などを含む |
| `rx_port_outside` / `port_outside` | TCP に到達したが宛先ポートが設定フロー範囲外 |
| `rx_tuple_mismatch` / `tuple_mismatch` | 宛先ポートはフロー範囲内だが版、アドレス、送信元ポート等が一致せず、フローと照合できない |
| `rx_neighbor` / `neighbor` | 外側または内側の ARP / IPv6 ND (ICMPv6 type 133–137) |
| `rx_other` / `other` | TCP 以外の通常通信 (通常 UDP、ICMP 等) |
| `rx_invalid_tcp` / `invalid_tcp` | 照合後に TCP ヘッダ長、IP 長、Timestamp オプションの形式検査で DROP |

`parse_failed` の詳細理由を既存パーサーから返すと、正常経路の戻り値処理・命令列にも影響する。
今回はこの制約を優先し、詳細理由はまとめる。
失敗経路の再解析は既存の層パーサーを再利用し、末端の ARP/ND や通常の非 TCP を補助的に識別する。
不正なパケットと未対応形式の判別には限界があり、これらの値だけで xdperf 応答の取りこぼしとは断定できない。
通常 UDP を受信する既存 tail call と PASS/DROP/TX の挙動は維持する。

Go は全 CPU 分を合算し、mixed final statistics と `xdperf.mixed.rx` ObservableCounter (`reason` 属性、単位 `{packet}`) に出す。
混合モード以外ではこのメトリクスを登録しない。
終了時の `tuple_mismatch > 0` は警告とし、計測自体はエラー終了させない。
利用者向け文書に各分類、ポート衝突、アドレス/NAT、対向設定、未対応トンネルや MTU の確認順序を記す。

検証では BPF_PROG_RUN で全分類と正常照合、内外の ARP/ND、IPv4/IPv6、各照合要素と不正長を確認する。
既存 examples の正常 E2E に `tuple_mismatch == 0` の検査を追加する。
変更前後の BPF オブジェクトを同じコンパイラで比較し、通常モードの全プログラムと正常 RX 経路 (分岐先の再配置を除く) の命令を検算する。
全 sudo race テスト、examples、lint、複数レビュアーによる OCR を実行してから #125 を push する。
#126 へ merge した後も取り込み差分の OCR と検証を行い、両 PR の Copilot と CI を完了させる。PR 自体はマージしない。
性能測定は行わない。検証ログと比較用オブジェクトは `out/rx-diagnostics/` に保存し、Git には検算スクリプトと文書だけを残す。

### 実装方針の補足: 不正 TCP の cold 分岐

LLVM 22 では不正 TCP の return に C のカウンタ呼び出しを加えるだけでも、関数全体のレジスタ割り当てと spill が変わった。
固定レジスタや空の asm による誘導も正常経路の完全一致を保証できず、保守性が低いため採用しない。
一方、unmatched への void 関数呼び出しだけなら正常経路は分岐先の再配置を除いて完全一致した。
そこで不正 TCP の既存 C 分岐は変更せず、混合プログラムのロード時にその三つの長さ検査の分岐先だけを専用ブロックへ差し替える。
専用ブロックは既存の PERCPU 加算関数を呼び DROP する。正常経路に命令は挿入しない。
BTF の元ソース行、分岐命令の種類と数、共通の旧分岐先を検査し、コンパイラ更新等で構造が変わった場合は明示的なエラーにする。
既存の混合プログラムのロード前処理 (機能別定数の設定) と同じ箇所に限定し、実行用の collection 読み込みと混合プログラムの読み込みで適用する。
生の `LoadBpf()` spec を手動で読み込む場合は `PrepareMixedRXDiagnostics` を明示的に呼ぶ。
変更前のオブジェクトとの検算では、このロード時処理後も比較する。

外側 ARP/ND 等は dispatcher の PASS からも分類関数に入れる。
通常 TCP を dispatcher から振り分ける既存の命令列は維持し、tail call 先での二重加算はしない。
