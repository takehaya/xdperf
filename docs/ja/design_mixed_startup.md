# 混合モードの起動時間短縮

## 実装前の計画

比較元は main の `7b16bbc`（#120）とする。
混合モードは通常の BPF ロード後にプラグイン応答を処理し、混合専用の 4 プログラムを追加ロードする。
既存の測定では追加ロードに約 3.9 秒かかり、混合 TCP TX と RX の検証が大半を占めた。

検証済み TCP テンプレートから、外側ヘッダの修正数、UDP チェックサム LCO の有無、チェックサム計算範囲の上限を求める。
全グループの最大値を混合専用の読み取り専用定数に設定し、展開済みループの不要な反復を verifier が除去できるようにする。
この設定は混合 TCP TX と RX 応答の共通 builder にだけ適用する。
通常の packet と `--tcp` のエントリポイント、ロード順序、定数は変更しない。
混合専用定数は別の rodata セクションに置き、既存コレクションの凍結済み定数マップから分離する。
設定を省略するロードテストでは全機能を有効にする。

送信に使わないトンネルの RX 解析を削除する案は採用しない。
[既存設計](design_tcp_flow_template.md#受信側とフロー照合) は外側経路の非対称性を許しており、送信テンプレートだけでは受信するトンネル形式や深さを制限できないためである。
GENEVE オプションを含む RX 解析は従来の受理範囲を保つ。
RX の応答 builder も送信テンプレートを使うので、こちらは安全に縮小できる。

BPF とプラグインの並行ロードは最初の実装には含めない。
まず追加ロードの主要因を減らして測定し、残る起動時間に対して効果が見込める場合に検討する。
packet の既存起動経路を保つ条件と、初期化失敗時のリソース解放を優先する。

## 検証計画

- 機能選択の単体テストで、非カプセル化、LCO あり／なし、複数グループ、入れ子の上限を確認する。
- BPF ロードテストとパケット検証で、特化した TX と RX 応答のチェックサム、長さ、フロー状態を確認する。
- 再生成前後で packet と通常 TCP の BPF 命令を比較し、ロード後の tag とサイズも照合する。
- `go test -v -exec sudo -race ./...`、examples の E2E、lint、OCR レビューを通す。
- PR 作成後に Copilot レビューを依頼し、妥当な指摘を修正する。CI の 6.1 以降のカーネル検証を含め、全チェックの完了を待つ。マージはしない。

性能測定は既存 mixbench のスクリプトを作業ディレクトリ内の `out/mixbench/` に複製して行う。
比較元と変更後を同じ Go 1.25.5 でビルドし、バイナリのハッシュとコミットを記録する。
非カプセル化、VXLAN、GENEVE、packet 専用について 1／4 worker、6 ブロック、各 8 秒で測定する。
全条件で base/head を隣接させ、順序を無作為化する。
対応差の平均と t 分布による両側 95% 信頼区間を、起動秒数、packet pps、TCP goodput について示す。
packet 定常区間の算出方法は既存手順を継承する。
有意な性能低下があれば原因を調べて修正し、信頼区間が広い場合はその限界も記録する。
通常 TCP の起動も別途対応比較する。
生データ、実行順、コマンド、環境情報、ログ、再集計スクリプトを残す。

## 実装中の判断

LCO の内側ループに計算範囲の定数上限を入れた最初の実装では、複数トンネルを含むパケットテストが verifier の 100 万検証命令上限を超えた。
範囲の制限を取り除き、長さ修正数、外側 IP 数、UDP 数と LCO の有無だけを定数にした構成では同じテストを通過した。
この構成を採用し、LCO の内側ループと RX 解析器の展開上限は維持する。

全ファイルの lint には既存の失敗があった。
`jq -e empty` は正常な JSON にも終了コード 4 を返すため、構文検査を `jq empty` に直す。
併せて既存の YAML インデントと、lint が自動修正する 2 ファイルの末尾空白を整える。
