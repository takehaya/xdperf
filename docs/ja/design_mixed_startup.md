# 混合モードの起動時間短縮

## 実装前の計画

比較元は main の `7b16bbc`（#120）とする。
混合モードは通常の BPF ロード後にプラグイン応答を処理し、混合専用の 4 プログラムを追加ロードする。
既存の測定では追加ロードに約 3.9 秒かかり、混合 TCP TX と RX の検証が大半を占めた。

検証済み TCP テンプレートから、外側ヘッダの修正数、UDP チェックサム LCO の有無、チェックサム計算範囲の上限を求める。
全グループの最大値を混合専用の読み取り専用定数に設定し、展開済みループの不要な反復を verifier が除去できるようにする。
この設定は混合 TCP TX と RX 応答の共通 builder にだけ適用する。
通常の packet と `--tcp` のエントリポイント、ロード順序、定数は変更しない。
混合専用定数は別の rodata セクションに置き、既存コレクションの凍結済み定数マップから分離する。
設定を省略するロードテストでは全機能を有効にする。

送信に使わないトンネルの RX 解析を削除する案は採用しない。
[既存設計](design_tcp_flow_template.md#受信側とフロー照合) は外側経路の非対称性を許しており、送信テンプレートだけでは受信するトンネル形式や深さを制限できないためである。
GENEVE オプションを含む RX 解析は従来の受理範囲を保つ。
RX の応答 builder も送信テンプレートを使うので、こちらは安全に縮小できる。

BPF とプラグインの並行ロードは最初の実装には含めない。
まず追加ロードの主要因を減らして測定し、残る起動時間に対して効果が見込める場合に検討する。
packet の既存起動経路を保つ条件と、初期化失敗時のリソース解放を優先する。

## 検証計画

- 機能選択の単体テストで、非カプセル化、LCO あり／なし、複数グループ、入れ子の上限を確認する。
- BPF ロードテストとパケット検証で、特化した TX と RX 応答のチェックサム、長さ、フロー状態を確認する。
- 再生成前後で packet と通常 TCP の BPF 命令を比較し、ロード後の tag とサイズも照合する。
- `go test -v -exec sudo -race ./...`、examples の E2E、lint、OCR レビューを通す。
- PR 作成後に Copilot レビューを依頼し、妥当な指摘を修正する。CI の 6.1 以降のカーネル検証を含め、全チェックの完了を待つ。マージはしない。

性能測定は既存 mixbench のスクリプトを作業ディレクトリ内の `out/mixbench/` に複製して行う。
比較元と変更後を同じ Go 1.25.5 でビルドし、バイナリのハッシュとコミットを記録する。
非カプセル化、VXLAN、GENEVE、packet 専用について 1／4 worker、6 ブロック、各 8 秒で測定する。
全条件で base/head を隣接させ、順序を無作為化する。
対応差の平均と t 分布による両側 95% 信頼区間を、起動秒数、packet pps、TCP goodput について示す。
packet 定常区間の算出方法は既存手順を継承する。
有意な性能低下があれば原因を調べて修正し、信頼区間が広い場合はその限界も記録する。
通常 TCP の起動も別途対応比較する。
生データ、実行順、コマンド、環境情報、ログ、再集計スクリプトを残す。

## 実装中の判断

LCO の内側ループに計算範囲の定数上限を入れた最初の実装では、複数トンネルを含むパケットテストが verifier の 100 万検証命令上限を超えた。
範囲の制限を取り除き、長さ修正数、外側 IP 数、UDP 数と LCO の有無だけを定数にした構成では同じテストを通過した。
この構成を採用し、LCO の内側ループと RX 解析器の展開上限は維持する。

全ファイルの lint には既存の失敗があった。
`jq -e empty` は正常な JSON にも終了コード 4 を返すため、構文検査を `jq empty` に直す。
併せて既存の YAML インデントと、lint が自動修正する 2 ファイルの末尾空白を整える。

packet TX/RX、checksum の 3 段、通常 TCP TX/RX、TCP server RX の 8 プログラムは、main と再配置済み BPF 命令バイト列が完全一致した。
比較スクリプトと SHA-256 は `out/mixbench/compare.go` と `bytecode.txt` に保存した。

設計上の前提は [混合バリアント](design_mixed_variants.md)、[TCP フローひな型](design_tcp_flow_template.md)、[XDP TCP エンジン](design_xdp_tcp.md) を参照する。

ロード後の同一性は BPF tag と `bytes_xlated` で確認する。
既存 packet プログラムの一部では、tag と変換後 BPF 長が同じでも `bytes_jited` に試行間で 3〜6 バイトの差を観測した。
JIT サイズの完全一致を BPF バイトコード不変の判定には使わず、各試行の値は生データに残す。

## 初回測定で検出した回帰と修正

初回実装 `8844011` の 96 試行は、エラーと再送が 0 で、全フローの受信バイト数が一致した。
起動時間は非カプセル化で約 27%、VXLAN/GENEVE で約 20% 短縮した。
しかし非カプセル化の 1 worker では packet pps が −2.72%［95% CI: −4.62%, −0.81%］、TCP goodput が −2.76%［−4.69%, −0.83%］となり、性能の完了条件を満たさなかった。
この 6 ブロックのデータとバイナリは `out/mixbench/` にそのまま保存する。

修正では、外側の長さ修正が一つも必要ないときに、カプセル化修正 helper の呼び出し自体を省く。
対応する外側 IP/UDP ヘッダには必ず長さ修正があるため、非カプセル化と MPLS のみのテンプレートはこの条件で区別できる。
内側 IP/TCP の修正は先に完了している。
初回実装ではこの条件でも helper に入り、上限定数のロードとテンプレートの検査が残っていた。

修正後の測定は `out/mixbench2/` に分離し、同じ 96 試行を新たに完走する。
初回の不利な試行を除外したり、修正後の結果と混ぜたりしない。

## 測定条件と最終版の命令数

比較元は main `7b16bbc`、最終版は `ec28839`。
小さな集計 CSV と検算スクリプトは [測定資料](benchmarks/mixed-startup/README.md) に収録する。
生データと実行ファイルのハッシュ一覧は git 管理外の `out/` に保全し、保存場所と検算コマンドは同 README に記載する。
全 3 回とも 6 ブロックの対応比較とし、各 8 秒、1／4 worker、混合比率 3:1、TCP 4 flow、MSS 1024、window 32 で実行した。
VXLAN／GENEVE は外側 IPv4/UDP LCO、内側 Ethernet/IPv4/TCP を使用した。
起動時間はプロセス起動から送信開始ログまで、混合スループットは送信開始から drain 開始までの時間と最終カウンタから求める。
packet 専用は統計ログの最初の 6 区間から定常 pps を求める。
対応差と対応変化率は各ブロックで計算し、t 分布（自由度 5）による両側 95% CI を示す。
多重比較補正は行わない。

ロード後の BPF 命令数（`bytes_xlated / 8`）は次のとおり。
RX 解析器は共通のままで、RX も応答パケットを作る処理の特化により小さくなる。

修正版では affected な混合・TCP・BPF ロードテストと追加 MPLS テストを sudo race で再実行し、mixed／tcp-template／tcp-vxlan の E2E も再実行して成功した。
OCR の追加ラウンドでも 4 人が確認し、MPLS prefix とフレーム長の検証追加に対応した。
初回の全テスト・全 12 E2E と、修正版での再実行範囲は区別して記録する。

## 基底ロードから混合専用定数を除外

再確認で、自動生成された `BpfVariables` の埋め込みにより、混合専用の `.rodata.mixed` も基底ロード時に割り当てられることを見つけた。
`ebpf` の変数割当は、その変数が属するマップもロードする。
packet と通常 TCP の起動経路を保つため、基底ロードの対象を従来の 6 変数に限定する。
既存の変数の戻り値と寿命は保ち、混合専用定数は後続の混合プログラムのロード時にだけ使用する。

この変更自体は Go の初期化処理だけで、BPF オブジェクトは変わらない。
ただし下記の 2 回目の測定でも性能低下を検出したため、BPF 側も追加で修正し、最終版では全 96 試行を再測定する。

## 2 回目の測定で検出した VXLAN の回帰

`ae262c4` の全 96 試行ではエラー・再送 0、全フローの受信バイト数が一致した。
非カプセル化 1 worker の有意な低下は解消したが、VXLAN 1 worker の packet pps は −1.05%［95% CI: −1.77%, −0.32%］、TCP goodput は −1.09%［−1.88%, −0.31%］で、まだ完了条件を満たさなかった。
データとバイナリは `out/mixbench2/`、集計は `benchmarks/mixed-startup/second/summary.csv` に保存する。

展開した各反復で `const volatile` の上限を再読込していたため、verifier が分岐を削除した後にも不要なロードが残る。
各ループの直前で上限を一度だけ読み、LCO の有無も UDP ループの外で一度だけ読む形に変更する。
基底ロードの修正も含む最終版を `out/mixbench3/` で再測定する。
不利だった前 2 回の結果は残し、最終版の集計には混ぜない。

## 最終版のローカル検証

`ec28839` で `make test`（全パッケージの sudo race）、全 12 examples E2E、`make lint` を再実行して成功した。
基底ロードの混合変数未割当と従来変数の読み取りも確認した。
packet／通常 TCP の既存 8 プログラムの再配置済み命令は、最終版でも main と完全一致した。
OCR の追加ラウンドは 4 人の独立レビューで未対応の指摘がない。
最終版の全 96 試行と通常 TCP 起動の 6 対を `out/mixbench3/` に保存する。

## 最終測定結果

全 96 試行でエラー・再送は 0、全フローが終了し、ACK 済みバイト数と sink の受信バイト数が一致した。
最終版では混合モードの起動時間が全条件で有意に短くなり、非カプセル化で約 27〜28%、VXLAN／GENEVE で約 19% 短縮した。
packet pps と TCP goodput には、今回の対応差の 95% CI で有意な低下を検出しなかった。
ただし非カプセル化 1 worker の変化率 CI は約 −5% まで広がっており、同等性や小さな低下がないことを証明する結果ではない。
測定はこのホストの veth、外側 IPv4/LCO、1／4 worker に限定され、他の NIC、トンネル構成、カーネルでの性能を保証しない。
旧カーネルの互換性は別途 CI のロード検証で確認する。

表の対応差は `head - main`、対応変化率は各ブロックの `100 * (head / main - 1)` の平均である。
変化率の平均は平均値同士の比とは異なる。
